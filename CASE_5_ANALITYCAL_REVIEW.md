# Кейс-задача №5
## Аналитический обзор кейс-задачи №4
### WEB-приложение «Туризм» (FastAPI + PostgreSQL)

## Введение
В рамках кейс-задачи №4 разработано учебное WEB-приложение в предметной области «Туризм» с клиент-серверной архитектурой: FastAPI (backend/API) + PostgreSQL (хранение данных) + Docker Compose (развертывание).

Цель данного обзора: оценить качество решения по критериям кейс-задачи №5, выявить риски текущего MVP и предложить конкретные шаги для развития системы.

## Объект анализа
В обзор включены фактические артефакты проекта:
- API и маршруты: `app/main.py`, `app/routers/health.py`, `app/routers/tours.py`, `app/routers/orders.py`
- доступ к БД и модели: `app/db.py`, `app/models.py`, `app/schemas.py`
- схема и начальные данные: `sql/init.sql`
- контейнеризация: `Dockerfile`, `docker-compose.yml`
- эксплуатационная документация: `README.md`

## Ключевые findings (по важности)
Ниже перечислены основные технические замечания в формате code review (severity -> impact -> решение).

1. `High` Отсутствует аутентификация и авторизация для работы с заявками.
   Факт: эндпойнты `GET /orders` и `POST /orders` доступны без защиты (`app/routers/orders.py:12`, `app/routers/orders.py:18`).
   Риск: несанкционированный просмотр/создание заявок, утечка персональных данных.
   Решение: JWT/OAuth2, разграничение ролей (например, `admin/manager/client`), ограничение чтения списка заявок.

2. `High` Отсутствуют автоматические тесты.
   Факт: в репозитории нет тестового пакета (`tests/`), запуск подтверждается ручными вызовами через Swagger/curl.
   Риск: высокий шанс регрессий при изменении API/моделей.
   Решение: базовый набор `pytest` + `FastAPI TestClient` + CI-проверка.

3. `Medium` Нет миграций БД; используется только инициализационный SQL-скрипт.
   Факт: структура создается через `sql/init.sql`, без Alembic.
   Риск: сложные и рискованные изменения схемы на живых данных.
   Решение: подключить Alembic, вести версионирование схемы и миграции данных.

4. `Medium` Нет пагинации/фильтрации списков.
   Факт: `GET /orders` и `GET /tours` возвращают полный набор записей (`app/routers/orders.py:12`, `app/routers/tours.py:12`).
   Риск: деградация производительности и UX при росте данных.
   Решение: `limit/offset`, сортировка/фильтрация, индексы под рабочие запросы.

5. `Medium` Несогласованность типов в ORM-модели заказа.
   Факт: поля `start_date` и `created_at` объявлены как `Mapped[str]` при колонках `Date` и `DateTime` (`app/models.py:30`, `app/models.py:32`).
   Риск: ошибки статической типизации и технический долг.
   Решение: использовать `Mapped[date]` и `Mapped[datetime]`.

6. `Low` В `sql/init.sql` видны проблемы кодировки seed-данных.
   Факт: текст туров отображается в искаженном виде (`sql/init.sql:23`, `sql/init.sql:24`).
   Риск: некорректное отображение данных в БД/Swagger.
   Решение: сохранить файл в UTF-8 и пересоздать seed-данные.

## 1. Функциональность
### Что реализовано
- Проверка доступности сервиса: `GET /health` (`app/routers/health.py:6`)
- Получение списка активных туров: `GET /tours` (`app/routers/tours.py:12`)
- Создание заявки: `POST /orders` (`app/routers/orders.py:18`)
- Получение списка заявок: `GET /orders` (`app/routers/orders.py:12`)
- OpenAPI/Swagger генерируется автоматически через FastAPI (`app/main.py:7`)
- Реляционная структура БД с внешним ключом `orders.tour_id -> tours.tour_id` (`sql/init.sql:15`)

### Оценка
Функциональность учебного MVP соответствует кейсу №4: REST API, клиент-серверная архитектура, реляционная БД, SQL-инициализация.

### Вывод
Базовый функционал выполнен корректно, но ограничен до CRUD-минимума без продвинутых сценариев домена (статусы заказов, отмена, поиск, фильтры, история изменений).

## 2. Производительность
### Текущее состояние
- Запросы простые, без тяжелых JOIN/агрегаций (`app/routers/tours.py:14`, `app/routers/orders.py:14`).
- SQLAlchemy работает синхронно через `psycopg` (`app/db.py:10`).
- Контейнеры облегчены: `python:3.12-slim`, `postgres:16-alpine` (`Dockerfile:1`, `docker-compose.yml:3`).

### Потенциальные ограничения
- Нет пагинации в списках.
- Нет индексов, кроме PK/FK, для будущих фильтров и аналитики.
- Нет кэширования для часто читаемых данных (каталог туров).

### Рекомендации
- Добавить `limit/offset` для `GET /orders`, `GET /tours`.
- Добавить индексы по `orders.created_at`, `orders.tour_id`, возможно `tours.is_active`.
- При росте нагрузки внедрить Redis-кэш на read-heavy эндпойнтах.

## 3. Удобство использования (юзабилити)
### Плюсы
- Swagger UI позволяет тестировать API без отдельного клиента.
- Ясные схемы запроса/ответа через Pydantic (`app/schemas.py`).
- Команды запуска и обслуживания подробно описаны в `README.md`.

### Ограничения
- Нет отдельного пользовательского frontend-интерфейса.
- Ошибки домена минимальные (например, только `Tour not found or inactive`).
- Нет локализации сообщений и дружелюбных бизнес-объяснений.

### Рекомендации
- Добавить простой frontend (React/Vue или серверные шаблоны).
- Ввести унифицированный формат ошибок (код/сообщение/подробности).
- Расширить валидацию телефона/имени и бизнес-правил бронирования.

## 4. Безопасность
### Текущее состояние
- Аутентификация и авторизация отсутствуют.
- Доступ к заявкам открыт.
- Ограничение частоты запросов не реализовано.
- Секреты/пароли пока в compose-файле (для учебного контура допустимо, для production нет).

### Риски
- Утечка персональных данных заявок.
- Спам-заявки и возможные DoS-паттерны на открытых маршрутах.
- Отсутствие аудита и управления правами.

### Рекомендации
- JWT + role-based access control.
- Rate limiting (например, SlowAPI/Nginx).
- HTTPS в прод-среде (reverse proxy: Nginx/Traefik).
- Секреты через `.env`/secret manager, а не напрямую в compose.

## 5. Масштабируемость
### Сильные стороны
- API и БД разделены по сервисам (`docker-compose.yml`).
- Контейнеризация упрощает горизонтальное масштабирование API.
- Архитектура роутеров допускает добавление новых доменных модулей.

### Ограничения
- Нет healthcheck/readiness в compose для координации старта.
- Нет очередей/фоновых обработчиков для асинхронных задач.
- Нет внешнего мониторинга и метрик.

### Рекомендации
- Добавить healthcheck для `db` и `api`, условные зависимости по health.
- Для тяжелых задач: Celery/RQ + Redis/RabbitMQ.
- Мониторинг: Prometheus + Grafana, centralized logging.

## 6. Сопровождаемость
### Плюсы
- Логичная структура: routers/models/schemas/db.
- Отделены схема БД и API-слой.
- Документация запуска и эксплуатации присутствует.

### Ограничения
- Нет миграций.
- Бизнес-логика пока внутри роутеров, без сервисного слоя.
- Версии зависимостей не закреплены жестко.

### Рекомендации
- Добавить Alembic.
- Вынести доменную логику в `services/`.
- Ввести линтер/форматтер/типизацию (`ruff`, `black`, `mypy`) и pre-commit.

## 7. Переносимость
### Плюсы
- Docker Compose обеспечивает переносимость между Windows/Linux/macOS.
- Образы стандартные и совместимые (`python:3.12-slim`, `postgres:16-alpine`).

### Нюанс
- Для запуска без Docker требуется ручная настройка БД и переменных среды.

### Рекомендации
- Добавить `Makefile`/скрипты для унификации команд.
- Добавить профиль `dev`/`prod` в compose-конфигурации.

## 8. Качество кода
### Положительные аспекты
- Четкое разделение слоев API/модели/схемы.
- Простые, понятные маршруты.
- Используются ограничения валидации Pydantic (`app/schemas.py:17-22`).

### Зоны роста
- Исправить типы ORM для дат/времени.
- Централизовать обработку ошибок.
- Добавить соглашения именования, docstrings, единый style guide.

## 9. Тестирование
### Текущее состояние
- Ручное тестирование через Swagger и curl.
- Smoke-проверка `GET /health`.

### Недостатки
- Нет unit/integration тестов.
- Нет проверки миграций и сценариев ошибок.

### Рекомендации
- `pytest` + `TestClient` + временная тестовая БД.
- Интеграционные тесты ключевых сценариев: создание заказа, валидация, 404 для неактивных туров.
- Покрытие и минимальный порог в CI.

## Выявленные проблемы и способы решения
| Проблема | Текущее проявление | Предлагаемое решение |
|---|---|---|
| Нет авторизации | Открытые `/orders` | JWT + RBAC |
| Нет пагинации | Полные выборки списков | `limit/offset`, фильтры |
| Нет миграций | Только `sql/init.sql` | Alembic |
| Нет автотестов | Ручные проверки | `pytest` + CI |
| Нет индексов под рост данных | Потенциальные медленные чтения | Индексы по `created_at`, `tour_id` |

## Приоритетный план развития
1. `P1 (критично)` Безопасность и доступ: JWT, RBAC, ограничение чтения заказов, rate limiting.
2. `P1 (критично)` Качество поставки: автотесты + CI + базовые проверки качества кода.
3. `P2` Миграции и эволюция БД: Alembic + регламент изменений схемы.
4. `P2` Производительность: пагинация, индексы, оптимизация запросов.
5. `P3` UX: простой frontend и улучшенные доменные ошибки.
6. `P3` Эксплуатация: healthchecks, мониторинг, централизованные логи.

## Заключение
Проект кейс-задачи №4 успешно реализует учебный MVP WEB-приложения «Туризм» и полностью закрывает базовые требования задания: клиент-серверная архитектура, REST API, реляционная база данных и контейнерный запуск.

Для перехода от учебного решения к production-уровню ключевыми шагами являются: усиление безопасности, автоматизация тестирования, внедрение миграций и доработка эксплуатационных практик.

В текущем состоянии проект является качественной базой для дальнейшего расширения функциональности и масштабирования.
